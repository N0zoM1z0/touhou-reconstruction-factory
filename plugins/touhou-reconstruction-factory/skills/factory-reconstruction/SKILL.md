# Factory Reconstruction

Follow contract `gpt-web-reconstruction-session-v1`. Coordinate the analysis,
workspace, and replay authorities without merging their evidence states.

## Establish the session

1. Require a game ID, concrete objective, and measurable stop condition. A scope
   hint is optional. If they are broad, discover enough committed context to
   choose one bounded work packet before editing.
2. Call `factory_describe` and `factory_list_repositories`. Use only returned
   identities. If the user supplies a workspace ID, resume it with
   `factory_get_workspace`; otherwise create one workspace with a stable unique
   idempotency key.
3. Report its committed baseline, expiry, and dirty-state observation. Dirty,
   untracked, ignored, and private canonical inputs are deliberately absent;
   never infer their content or overwrite them.
4. Read committed repository instructions and its build, ledger, and test
   conventions. Keep reads, searches, analysis queries, and output pages narrow.

## Reconstruct

1. State the bounded functions, addresses, bytes, files, evidence, unknowns, and
   stop condition. Do not report a completion percentage without an independently
   supported boundary and denominator.
2. Use the `factory-analysis` workflow for semantic hypotheses. Discover the
   registered provider and operation, require target attestation, and preserve
   `exactness_credit="none"`, incompleteness, truncation, and errors.
3. Correlate analysis with committed source. Write maintainable natural C or C++.
   Inline assembly, embedded machine-code bytes, generated byte arrays, data
   masquerading as source, and oracle-specific tricks are not routine solutions.
   Stop and explain the evidence before proposing a genuinely necessary minimal
   exception.
4. Use the `factory-workspace` workflow to edit and test. Run cheap focused
   feedback before broader repository-native checks. Page truncated output.
   Treat unavailable private targets or toolchains as unavailable.
5. Avoid raw analysis dumps, chat journals, duplicated decompiler output, and
   stale scratch artifacts. Prefer curated source, tests, ledgers, and concise
   durable documentation.

## Preserve the evidence boundary

- Analysis output is provisional and has no exactness credit.
- Workspace results are candidate engineering evidence. They neither edit
  canonical source nor enter the Truth Kernel.
- Use `factory-replay` only for a discovered claim already bound to canonical
  committed source, never for the current disposable diff.
- Job completion, receipt verdict, and registry acceptance are distinct.
- Imported progress, comments, prior agent work, and external references are
  candidates until independently checked.
- Unknown is preferable to a guessed identity, extent, ownership, provenance,
  equivalence, or exactness conclusion.

Do not kill or reconfigure unrelated processes. Do not discard a resumable
workspace unless the user explicitly asks or says it is no longer needed. Stop
this Web workflow after reverse analysis, source reconstruction, and
compile/build/link feedback; game runtime and portability work belong in the
local Codex handoff.

## Handoff

Always report:

- session status: stop condition met, blocked, or bounded progress;
- game, objective, completed scope, and excluded scope;
- baseline commit, dirty-state observation, workspace ID, and expiry;
- analysis provider, target attestation, evidence, and exactness limitation;
- changed files and rationale;
- tests actually run and checks unavailable;
- complete diff byte size and whole-diff SHA-256;
- accepted Truth Kernel facts separately from candidate results;
- unknowns, blockers, and next local action;
- a proposed English commit message beginning with `gpt-web:`.

Keep the workspace available for reconnect and local review. The normal next
step is for local Codex to review and apply the diff to the canonical game
repository, then discover and replay an eligible canonical claim.
